## Registry path and architectural risks

The current `UReal33DAssetRegistry` (`unreal/REAL33D/Source/REAL33D/Public/Real33DAssetRegistry.h` and `Private/Real33DAssetRegistry.cpp`) loads only engine primitives. `ResolveGround(TypeId)` and `ResolveThing(TypeId,bBlocking)` can later consult a reviewed `TypeId -> tracker ID -> approved asset` table and return a mesh/material, scale and offset; their placeholder fallback remains for everything else. `AReal33DTile::ApplyStack` already asks those methods for each ordered stack item. The first conditional sample therefore needs only an approved mapping/catalogue, imported mesh/material assets under Unreal `Content/`, and registry code/configuration; it does not need a protocol, WorldState, movement or server change. The exact content paths cannot be named until source files exist.

Creature integration has an additional boundary: `ResolveCreature` receives a session `CreatureId` and local-player flag, neither a race nor an outfit. `WorldState::CreatureRecord` already holds an `OutfitDescriptor`, but `WorldEvent` and `FReal33DEvent` do not expose it; the current actor uses `UStaticMeshComponent`, not a skeletal component. A future creature sample must carry the demonstrated visual identity across the semantic event boundary and add skeletal presentation through the registry. Do not infer race from creature name or hardcode asset paths in an Actor. Keep creature work out of the first static sample unless a separately reviewed design establishes the event and presentation changes.
